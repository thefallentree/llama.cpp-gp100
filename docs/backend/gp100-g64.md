# Q4_1_G64 on Tesla P100 (GP100 / sm_60)

How to take **any** model llama.cpp can load and serve it as `Q4_1_G64` on
this fork. The type is **not** in stock [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp)
(`invalid ggml type 43`). Runtime pin:
[`thefallentree/llama.cpp-gp100@a8c9f3a7b`](https://github.com/thefallentree/llama.cpp-gp100/tree/a8c9f3a7b)
(tag `gp100-qwen38-g64slot`). **sm_60 only.** P40 / GTX 10-series are sm_61;
the HFMA2 path is gated off there.

Why this type exists (GP100 vs GP104, decode timeline, closed levers) is
written up on the measured pack card:
[DESIGN.md](https://huggingface.co/fallentree/Qwen3.8-27B-Uncensored-GP100-GGUF/blob/main/DESIGN.md).
This file is the **convert + serve** recipe for a new model.

## What you get

`block_q4_1_g64` = `half2 dm` + 32 nibble bytes = **36 B / 64 weights = 4.5 bpw**.
Same HFMA2 decode as Q4_1; fewer DRAM sectors. The fast CUDA path
(`mmvq-f16-sm60.cu`) accepts a weight when:

| constraint | value |
|---|---|
| type | `Q4_1_G64` (also Q4_1 / Q4_K / Q8_0) |
| `ne[0]` (K) | `% 64 == 0` for G64 (`% 32 == 0` for Q4_1) |
| `ne[1]` (rows) | `% 8 == 0` |
| `ne[2]` | `1` (except a G64 seq-fold for recurrent projections) |
| GPU | NVIDIA Pascal compute (`sm_60`), not DP4A (`sm_61+`) |

Tensors that miss those constraints still **load**. They go through
dequant + cuBLAS. Inspect the file before you serve so you know how much
of the model actually hits A16.

Do **not** G64 a draft model and share `token_embd` with a Q4_1-trained
drafter. Keep embeddings Q4_1 (or F16/Q8) unless you measured the draft.

## Convert

```bash
# 1. HF → high-precision GGUF (any arch convert_hf_to_gguf.py supports)
python convert_hf_to_gguf.py --outfile model-f16.gguf --outtype f16 /path/to/hf

# 2. Optional imatrix (same as any other llama.cpp quant)
./build/bin/llama-imatrix -m model-f16.gguf -f calibration.txt -o model.imatrix

# 3. Inspect, then quantize
python scripts/g64/convert_to_g64.py inspect model-f16.gguf
python scripts/g64/convert_to_g64.py convert model-f16.gguf model-g64.gguf \
    --imatrix model.imatrix \
    --quantize ./build/bin/llama-quantize
```

`convert` defaults:

| flag | default | why |
|---|---|---|
| `--mode auto` | `quantize` unless the body is already Q4_1 | F16→G64 is the quality path |
| `--output-tensor-type` | `q8_0` | G64 on a 100k–250k vocab head is a measurable PPL hit |
| `--token-embedding-type` | `q4_1` | exact-embd drafts; A16-friendly |
| `--pure` | always passed to `llama-quantize` | no surprise K-quant mix |
| `--allow-requantize` | auto-on if the source is already quantized | required for Q4_K / Q8 / Q4_1 sources |

Already-quantized sources work (`--allow-requantize`) but lose quality
versus F16. Prefer a F16/BF16 GGUF.

If the body is **already Q4_1** (mradermacher i1, etc.), `--mode auto`
picks **refit**: dequant each 32-weight Q4_1 block, fit one `(d,m)` per
64 weights (optional imatrix least-squares), rewrite nibbles. No F32
model on disk. This is how the published Qwen3.8 27B G64 file was built.

```bash
python scripts/g64/convert_to_g64.py convert model-q4_1.gguf model-g64.gguf --mode refit --imatrix model.imatrix
```

`llama-quantize Q4_1_G64` used to **abort** when any weight had `ne[0] % 64 != 0`.
It now falls back that tensor to Q4_1 (then F16 if even 32 does not divide).
`--output-tensor-type` / `--token-embedding-type` go through the same fallback.

Manual equivalent without the wrapper:

```bash
./build/bin/llama-quantize \
    --pure --allow-requantize \
    --output-tensor-type q8_0 \
    --token-embedding-type q4_1 \
    --imatrix model.imatrix \
    model-f16.gguf model-g64.gguf Q4_1_G64
```

Vision / mmproj stays a **separate** F16 or Q8 GGUF. Do not bake it into
the LLM file and do not G64 it — the projector is not on the decode
mat-vec path that G64 wins.

## Serve

Print a command:

```bash
python scripts/g64/convert_to_g64.py serve model-g64.gguf \
    --draft draft-q4_1.gguf --mmproj mmproj-f16.gguf --ctx 131072
```

Generic two-P100 recipe (tensor-split `1,1`, no NVLink, no peer atomics):

```bash
./build/bin/llama-server \
  --model model-g64.gguf \
  --jinja --backend-sampling \
  --graph-slots 8 \
  --ctx-checkpoints 8 --checkpoint-min-step 0 \
  --slot-prompt-similarity 0.05 \
  --device CUDA0,CUDA1 --split-mode tensor --tensor-split 1,1 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --ctx-size 131072 --flash-attn on
```

Add a draft only if you have one that matches this target’s
`token_embd` (Q4_1 exact, or the same G64 embedding you just wrote):

```bash
  --model-draft draft-q4_1.gguf --device-draft CUDA1 \
  --cache-type-k-draft q4_0 --cache-type-v-draft q4_0 \
  --spec-type ngram-mod,draft-dflash \
  --spec-draft-n-max 7 --spec-draft-n-min 0 \
  --spec-ngram-mod-n-min 7 --spec-ngram-mod-n-max 7
```

### Flags that depend on the architecture, not on G64

| If the model is… | do this |
|---|---|
| Hybrid / recurrent (Qwen GDN, Mamba, RWKV, …) | `--ctx-checkpoints` ≥ 1 and `--checkpoint-min-step 0`. Without a checkpoint the server forces `n_past=0` and you pay full prefill every turn. |
| Dense Transformer only | checkpoints optional; still cheap to leave on. |
| MoE | G64 applies to expert 2-D / 3-D weights the same way. Inspect `ne[2]`. The A16 hook wants `ne[2]==1` except the G64 seq-fold; expert `ne[2]>1` uses dequant+cuBLAS. |
| Needs a matching draft | keep `token_embd` at the draft’s type. Default Q4_1. |
| Short-prompt only traffic | G64 can **lose** the 1k / HumanEval wall versus Q4_1. Measure. The 10% no-spec win does not cover LoopSpec overhead on tiny prompts. |
| One P100 | drop `--device CUDA1` / `--tensor-split` / `--device-draft`. Draft on the same GPU serializes the ~5 ms GPU0 idle and is usually a loss when a second card exists. |

`--ctx-size` is **not** “G64 buys more context.” G64 shrinks **weights**.
Q8 KV at 155k / 190k still OOM’d a second turn on 2×16 GB with the 27B
pack. Pick a window that fits KV + graph-slots, then measure a cached
second turn before raising it.

`--graph-slots 8` needs the slot-release commits (`c22e06e8a`,
`a8c9f3a7b`) or a long prefill can OOM CUDA1 while the math says KV
fits. This pin has them.

## Closed levers (do not re-open from a new model)

Measured on GP100 against `DECODE_TIMELINE.md` (lab) / DESIGN.md. They
are not model-specific.

| lever | why closed |
|---|---|
| CUDA Graphs | Replays launches. Kernel gaps were 0.64 ms; graphs ON/OFF matched. |
| Draft on CUDA0 | Serializes GPU0 idle. Lost 5–6% at 16k. |
| G64 drafter + Q4_1-exact target embd | Hidden distribution bug. |
| Mixed-width LoopSpec (ngram 3..7) | Hash-unstable on the 27B G64 target. Constant 7..7 only. |
| FA `h2acc_ne=8` | Lost ngram accept. `h2acc_ne=4` is the pin. |
| L2 prefetch, `__ldcs`, ROWS=16, slice32/64 | Issue-bound kernel; occupancy / shared-memory was the wrong lever. |
| Stock llama.cpp | Type 43 unknown. |

## Check the file

```bash
python scripts/g64/convert_to_g64.py inspect model-g64.gguf --verbose
./build/bin/llama-perplexity -m model-g64.gguf -f wiki.test.raw --chunks 40
```

Publish gate used on the 27B pack: G64 wiki PPL within **+2%** of the
Q4_1 parent. Re-use that bar or write down a different one — do not
ship a G64 that you have not PPL’d against its parent.

`llama-bench -m model-g64.gguf -p 512 -n 128` at depth 0 / 1k / 16k is
the no-spec check. On the 27B pack that was **+10%** vs Q4_1. A new
arch will not automatically repeat that number; the byte win only
shows where the mat-vec is weight-stream bound.
